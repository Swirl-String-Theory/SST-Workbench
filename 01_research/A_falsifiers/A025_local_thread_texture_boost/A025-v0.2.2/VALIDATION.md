## v0.2.2 Windows build hotfix

The first real Windows run with Python 3.14.3, pybind11 3.1.0 and setuptools 84.0.0 exposed a packaging-only failure before C++ compilation:

```text
Multiple top-level packages discovered in a flat-layout: ['cpp', 'config', 'sst_thread_falsifier']
```

The generated setuptools build script now passes an explicit package list:

```python
packages=["sst_thread_falsifier", "sst_thread_falsifier.native_ext"]
```

This disables ambiguous flat-layout auto-discovery while leaving the extension target `sst_thread_falsifier.native_ext._native` unchanged.  This is a build-system correction only; no scientific gate or numerical kernel was altered.

The root `pyproject.toml` also declares the identical package list under `[tool.setuptools]`, so both the temporary native build and any root setuptools invocation avoid flat-layout auto-discovery.
## v0.2.2 Windows object-path hotfix

The v0.2.1 user run reached the real MSVC compiler, proving that explicit package discovery was fixed, but failed before C++ compilation with:

```text
fatal error C1083: Cannot open compiler generated file: '': Invalid argument
```

The emitted `/Fo` path mirrored the complete absolute repository path under setuptools' temporary directory and was about 350 characters in the reported checkout. v0.2.2 passes `cpp/native.cpp` as a relative source and forces `build\temp_native`, reducing the corresponding object path to roughly the repository root plus `\build\temp_native\cpp\native.obj`.

Static regression checks verify both guards. A real native PASS still requires the user's Windows/MSVC run; it is not claimed from the Linux packaging environment.
